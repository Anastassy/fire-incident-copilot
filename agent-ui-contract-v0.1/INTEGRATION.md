# Подключение

## 1. Контекст

Ведущий демо/сервер передаёт UI тройку context: demo_context_id, generation, subject_id. Это наши идентификаторы контекста, не существующие фильтры Data Platform. UI не придумывает их. generation меняется при новом проигрывании/перемотке, subject_id обозначает тему радио. Автоматическое сопоставление с источником ещё предстоит реализовать.

Каждый ответ и запрос явно привязан к этой тройке. Старый или недоступный контекст отклоняется: 409 CONTEXT_STALE либо 403. Проверка принадлежности обязательна и для evidence. Будущие относительно as_of данные агенту и UI не выдаются.

## 2. Методы

| Метод | Назначение |
|---|---|
| GET /agent/v1/state | Текущие ответы и карточки выбранного контекста |
| POST /agent/v1/questions | Принять вопрос, немедленно вернуть 202 и Answer со статусом queued |
| GET /agent/v1/questions/{request_id} | Прочитать состояние/результат вопроса |
| POST /agent/v1/questions/{request_id}/cancel | Отменить незавершённый вопрос |
| GET /agent/v1/cards/{hypothesis_id} | Получить текущую карточку |
| GET /agent/v1/evidence/{evidence_id} | Получить источник и актуальную ссылку на медиа |
| GET /agent/v1/events | SSE-подсказки об изменении сущностей |

Все GET и cancel требуют query-поля контекста. POST вопроса передаёт контекст в JSON. Повтор client_request_id с тем же телом в том же контексте возвращает ту же задачу, без второго модельного запуска. С другим телом — 409 IDEMPOTENCY_CONFLICT. Уже завершённый вопрос при cancel возвращается неизменённым; повторная отмена безопасна. Поздний результат отменённой задачи не публикуется.

## 3. Состояния

Answer: queued → running → ready / insufficient_data / error / cancelled. Терминальное состояние не откатывается в running. ready означает завершённый ответ на вопрос, а не подтверждённость каждого предполагаемого факта. Частичная выборка указывается в coverage даже у ready. Ошибка источника означает error, а не отсутствие подтверждения. При частично успешном поиске допускается ответ с полученными фактами и явными ограничениями.

Card.assessment: checking / supported / refuted / insufficient_data. Это результат проверки конкретного statement, а не опасность пожара. supported означает поддержку утверждения перечисленными источниками; оно не расширяется до перехода всей группы на канал.

Card.lifecycle: active / closed. Платформенный статус хранится отдельно; acknowledged не означает supported, resolved не означает выполнение поручения. Публикация uncertain/error не отменяет вычисленный результат, но UI явно показывает проблему синхронизации. В этой версии UI не меняет статус incident. Позже для операторских действий будет отдельный метод.

revision возрастает в пределах сущности и поколения. hypothesis_id сохраняется при проверке, появлении новых источников и изменении результата. При смене поколения прежние ID не используются в новом контексте. Состояния checking и supported показаны отдельными фикстурами одной карточки.

## 4. Доставка обновлений

SSE сообщает только type/context/entity_id/revision. Получив событие, UI запрашивает полную сущность GET. Это не текстовый поток модели. Queries содержит только реально выполненные обращения; фикстуры queries предназначены исключительно для мока UI и не должны выдаваться за живой запуск.

Начальное подключение: открыть SSE, затем получить state; накопленные сигналы обработать после snapshot. При разрыве оставить последние данные с пометкой времени, переподключиться и перечитать state. Периодически (ориентир 2 секунды в демо) перечитывать state как страховку: replay/курсор SSE в этой версии не обещается. Повторные и более старые entity revisions игнорировать. Snapshot не должен откатывать уже более новую локальную revision сущности. Удаление карточки не используется: она становится closed.

context.invalidated: отменить старые fetch, остановить плеер, очистить активное представление и ждать нового контекста от ведущего/сервера. Каждый запоздалый HTTP-ответ проверяется по context до применения. Пауза replay не меняет статус сетевого соединения.

## 5. Доказательства

Claim.evidence_ids непустой. Для ответа об отсутствии подтверждения основания включают существующие записи, а coverage и queries показывают границы поиска. Нельзя считать нулевой результат полным, если completeness=partial/unknown. Ссылки на конкретные claims разрешаются через GET evidence; evidence_ids верхнего уровня могут дополнительно включать контекст для unknowns.

reading_id — настоящий integer платформы; device_id — её UUID. В примерах это вымышленные значения, помеченные synthetic. Наш evidence_id — стабильный ID связки источника и фрагмента в выбранном контексте. Секреты и URL с токеном из raw_reading удаляются сервером.

Audio.start_ms/end_ms — начало включительно, конец исключительно, относительно файла по playback_url. UI использует start_ms/1000 и останавливает на end_ms/1000. Event_from_ms/event_until_ms — отдельная шкала времени сценария. Resolver на сервере преобразует смещение focus/WAV/AAC в шкалу возвращаемого файла. UI не прибавляет 292 секунды или 64 миллисекунды самостоятельно.

При availability=available обязательны рабочий playback_url, MIME и корректный интервал end>start. URL обслуживается через доверенный proxy/resolver, поддерживает seek и согласованный CORS. При pending/missing/error воспроизведение недоступно, источник и описание остаются видимыми. Истечение URL: заново GET evidence; не менять evidence_id. При неудаче загрузки показать ошибку, не подтверждать доступность. Сам URL не является постоянным идентификатором.

text_kind=description не показывать как дословную цитату. machine_transcript + not_human_verified явно отмечать. Предоставленные examples показывают missing: аудио в пакете отсутствует. Утверждения о реальном радио требуют ручной проверки исходника перед показом.

## 6. Авторизация и ошибки

Предлагается same-origin серверный прокси с HttpOnly сессией fire_ui_session. Он хранит ключ платформы; браузер его не получает. Это договорённость для реализации, не уже работающая авторизация. При иной топологии согласовать origin, credentials и CORS отдельно. Внешних записей до настройки доступа не выполнять.

Ошибка JSON: code/message/retryable/request_id. Коды: CONTEXT_STALE, IDEMPOTENCY_CONFLICT, NOT_FOUND, UNAUTHORIZED, FORBIDDEN, INVALID_REQUEST, UPSTREAM_UNAVAILABLE. Ответ 503 можно повторить с тем же client_request_id. Ошибки модели не включают секреты/сырой stack trace.

## 7. Семантические ограничения поверх JSON Schema

Все интервалы должны иметь конец не раньше начала; доступное аудио — строго позже. Checked interval не выходит за as_of_ms. completed_at заполнен у терминального Answer; error непустой только при status=error. Claims ready должны ссылаться на существующие источники того же контекста. closed требует closure_reason. platform_status=null допустим до создания incident. Полнота утверждается только после проверки источника и полного получения указанной выборки.
