# Firewatch — живой операторский экран

Тёмный рабочий интерфейс для State API и `/agent/v1` из main. Код без npm-зависимостей: ES modules, CSS, MediaSource и локальный Python gateway. Существующие макеты `dashboard/docs/design/` сохранены.

## Быстрый запуск

Из корня репозитория, сначала установить зависимости агента:

```sh
cd agent-service
uv sync --frozen
cd ..
python3 dashboard/live/run_local.py --state-config /absolute/path/to/state-api-client.json
```

Открыть **http://127.0.0.1:8790/**. Начальный запуск создаёт собственный paused run; нажать «Play». ID сохраняется в URL, поэтому перезагрузка этой страницы подключается к тому же запуску. Чтобы присоединиться к запуску команды, в настройках ввести его UUID. Чтобы создать другой — очистить поле UUID, выбрать сценарий и применить. Play, pause, seek и reset воздействуют на выбранный run и всех его подписчиков.

Приватный JSON вне репозитория содержит `base_url`, `read_token`, `control_token`. Альтернатива: переменные окружения `STATE_API_URL`, `STATE_READ_TOKEN`, `STATE_CONTROL_TOKEN`. Ключи поступают только в gateway; браузер не получает постоянные bearer-токены.

Launcher использует существующий агент на `127.0.0.1:8010`, если он доступен, либо запускает `agent-service/.venv/bin/python`. База по умолчанию находится в `agent-service/work/`; reset теста не сбрасывает другие сессии агента или State API. Ctrl+C останавливает только процессы, запущенные launcher.

Запуск каждого сервиса отдельно:

```sh
# Терминал 1, из agent-service/
uv run uvicorn fire_agents.api:create_app --factory --host 127.0.0.1 --port 8010

# Терминал 2, из корня репозитория
python3 dashboard/live/server.py --state-config /absolute/path/to/state-api-client.json --demo-agent
```

Сервер привязан к loopback. Не публиковать этот локальный gateway в интернете без отдельной аутентификации и HTTPS.

## Copilot как основной рабочий экран

Первым и самым крупным блоком показан Incident Copilot: вопрос агенту, последняя проверка с исходными сообщениями и неизвестными, вкладки Briefing / Checks / Questions. Три действия показывают назначение агента: открыть связанные доказательства, посмотреть проверки, прочитать ответы. Счётчики и статус работы берутся из snapshot агента; сырые события State API не засчитываются как обработанные агентом. Номера источников едины для карточек, ответов и списка доказательств внутри текущего snapshot.

Камеры, радио и показания находятся справа как источники для просмотра; полная лента и схема этажа — ниже. На узком экране Copilot остаётся первым. Тестовый режим и отсутствие связи его выводов с Base2 явно обозначены. Все прежние действия API доступны, включая evidence, полную карточку, coverage/queries, отмену и повтор вопроса.

## Что подключено

- State: snapshot + SSE, история опубликованных наблюдений, восстановление после разрыва/смены generation, play/pause/reset/seek и скорости 1×/10×/60×.
- Все опубликованные наблюдения: фильтры по типу, текстовый поиск, просмотр исходного JSON и provenance, выгрузка JSON. Лента сначала показывает последние 100 строк; «Show 100 more» открывает остальные. Полная опубликованная история подгружается страницами API и дедуплицируется с SSE.
- Две CCTV-камеры: один fMP4 HTTP-поток на камеру, переключение раскладки, полноэкранный просмотр, отдельный опубликованный видеофрагмент из ленты.
- Радио: один AAC fMP4-поток, явное включение звука, готовая машинная расшифровка по времени публикации, повторное прослушивание интервала реплики. Плеер повтора использует уже полученные байты и не занимает ещё одно постоянное HTTP-соединение.
- Агент: вопросы, фактические статусы и отмена, карточки проверок, claims, unknowns, coverage, queries, полные карточки, scoped evidence, состояния audio availability. SSE агента — уведомление: UI перечитывает state, дополнительно восстанавливается каждые 5 секунд.
- Отдельные состояния missing/stale/disconnected и null в показаниях. Нет выдуманного количества людей или общей оценки пожарной опасности.

Base2: синтетические видео и датчики, четыре окна записи `[0,15)`, `[68,83)`, `[128,143)`, `[176,191)` секунд. Между окнами плеер сохраняет последний полученный кадр с подписью об отсутствии новых кадров. Схема помещений условная. Историческое радио Palisades относится к другому событию; подписи источников не объединяют его в реальный инцидент с Base2.

Подача фрагментов задержана примерно на 2,15 секунды относительно часов сценария. Звук слушать на 1×; на 10×/60× он приостановлен, все текстовые и сенсорные события продолжают поступать. Повтор отдельной реплики всегда идёт на 1×. Транскрипция воспроизводится из исходного пакета, новая ASR в этом проекте не запускается.

## Настоящий агент и Data Platform

Без готовых URL используется локальный **FixtureEngine**, что явно подписано в UI. Это реальный API сервиса с детерминированным тестовым обработчиком, а не анализ поступающего эфира. Кнопки «1 · Request → 2 · Assign channel → 3 · Acknowledge» отправляют синтетические факты в отдельную сессию `dashboard-channel-demo-en`. Тестовые reading IDs не являются ID реальной платформы. Их аудио нельзя подменять записью Palisades.

Для реального сервиса запустить gateway **без `--demo-agent`**:

```sh
python3 dashboard/live/server.py \
  --state-config /absolute/path/to/state-api-client.json \
  --agent-url http://AGENT_HOST:8010 \
  --agent-context platform-demo --agent-generation 0 --subject platform
```

`FIRE_UI_SESSION_TOKEN` при необходимости передаётся gateway через окружение и добавляется в серверный запрос. Адрес агента задаётся при запуске gateway, контекст можно менять в UI.

Настройку SDK и импорта выполняет сервис агента по [его README](../../agent-service/README.md): `FIRE_ENGINE=sdk`, модель и ключ, `FIRE_PLATFORM_URL`, ключ платформы, фиксированный `FIRE_PLATFORM_SCOPE`. Импорт не продвигает часы автоматически. Команда backend должна согласовать session/generation/subject, границы источников и продвижение часов; UI не выдумывает platform reading IDs из State evidence IDs и не запускает собственный анализ.

Для будущего чтения ресурсов платформы gateway принимает `PLATFORM_API_URL` и `PLATFORM_API_KEY` и предоставляет ограниченный read-only `/api/platform/…`. Основной экран сейчас получает сырые данные непосредственно из State API, а выводы — из агента. Отдельный визуальный конструктор `/dashboards` Data Platform в этот экран не включён. В main у платформы `received_at` маппится в `ts`; это не позиция seek исторического аудио. Исходные simulation offsets остаются в provenance/payload.

## Проверки

```sh
node --test dashboard/live/tests/state.test.js
python3 -m unittest discover -s dashboard/live/tests -p 'test_*.py'
```

Тесты проверяют отсутствие смешения поколений/контекстов, пропуски последовательности, сохранение null/0, дубли SSE/истории, границы chunk/UTF-8 в SSE и защиту gateway от выдачи ключей и запросов вне разрешённых маршрутов.

Визуальная и сетевая приёмка описана в [VALIDATION.md](VALIDATION.md). Обзор реальных продуктов и разбор трёх сервисов — [исследование](../docs/research/LIVE_COMMAND_RESEARCH.md).

Интерфейс полностью на английском, вопросы отправляются с `language=en`. Английские названия устройств и сценариев — слой представления; исходные данные сохраняются. Английская тестовая сессия `dashboard-channel-demo-en` не изменяет ранее созданные сессии.
