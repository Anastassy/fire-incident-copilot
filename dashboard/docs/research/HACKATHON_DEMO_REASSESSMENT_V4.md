# Демонстрация Palisades: критерии конкурса и доказательство ценности

## Вывод

Главный демонстрационный момент — новое сообщение появляется в рабочем радиопотоке, после чего Copilot сам связывает его с запросом и меняет вывод. Оператор открывает оригинал и уточняет предел вывода. Жюри видит среду, самостоятельное действие агента и человеческую проверку в одном непрерывном сценарии.

Выразительный интерфейс помогает понять этот момент. Он не заменяет работающий агентский контур: официальная рубрика отдельно оценивает функциональность и техническую интеграцию. Детерминированный макет, даже использующий реальное аудио, остаётся макетом.

## 1. Повторная проверка правил

12 сентября 2026 повторно прочитаны раскрытый раздел Judging Criteria и Handbook на официальном портале Agents, Everywhere. Четыре критерия оцениваются от 1 до 5. Веса в процентах не опубликованы. Правила требуют двухминутное демонстрационное видео и публичный GitHub. Основная функциональность должна быть создана во время мероприятия; допустимы внешние библиотеки и заготовки. Нужно объяснить, что именно сделала команда.[1][2]

На момент проверки портал показывал подачу 12 сентября в 16:30 CEST. Наличие этой отметки не является подтверждением успешной подачи. Социальный пост с отметками партнёров входит в перечень подачи, но не выполняется задачей дизайна.[2]

## 2. Что было незаметно в V3

Большая надпись «ответ найден» читалась быстро, но скрывала работу по сопоставлению. Историю нужно было специально открывать. Жюри могло увидеть продукт как обычный чат с коротким ответом, не заметив, что он следит за источником в контексте инцидента.

V4 делает процесс наблюдаемым. Радиолента остаётся на экране, связанные записи получают одинаковое выделение, три звена заполняются по мере появления оснований. Это объясняет инновацию в одном взгляде: агент помогает удержать связь между сообщениями, пока продолжается радиообмен.

Кнопка Hide Copilot позволяет кратко показать ту же информацию без агентского слоя. Она не запускает другой сценарий и не выдаёт выдуманное сравнение скорости. Это визуальное объяснение вклада, а не эксперимент «до/после».

## 3. Что действительно готово в Git

Сверка начата с `44daa9d`; main содержал `3a7faec`. Во время работы появились merge V3 `307d06d` и перенос интерфейса в dashboard `fdf4282`. V4 развивается от `fdf4282` в отдельном worktree. Дополнительно прочитана ветка `origin/feat/platform` на `af86af5`. Ветка платформы не объединялась автоматически с текущей задачей.

| Компонент | Подтверждено чтением кода/документации | Что этим не подтверждено |
|---|---|---|
| Архив Palisades | Локальное аудио, ASR, происхождение и интервалы | Ручная точность ASR, личности говорящих, последствия конкретного обмена |
| agent-service | Локальные /agent/v1, асинхронные вопросы, snapshot, SSE, evidence; FixtureEngine по умолчанию | Работа реальной модели и live-платформы в этом показе |
| platform, отдельная ветка | REST/SSE/MCP, ingestion, мост к StateMachine, явная провенанца | Развёрнутый и проверенный сквозной путь на наших данных |
| StateMachine | Внешний компонент по документации команды | Авторство нашей команды и действующее соединение из V4 |
| V4 dashboard | Интерактивный replay, источники, цепочка и вопросы через заменяемые моки | Уже подключённые сервисы или автономное командование |

Есть важные несовпадения границ. Мост платформы использует received_at для ts, а интервалы симуляции сохраняет в payload. Аудиочанки им не переносятся как отдельные readings. Backend агента различает assessment, publication_status и platform_status; его supported нельзя превращать в «вся группа переключилась». Трём звеньям UI нужны явные роли источников, а не сортировка массива evidence по положению. Реальное аудио требует отдельного разрешения media_id в URL и интервал.

Техническую мощь стоит показывать в 90–105-й секундах реальными вызовами/данными: источник → платформа → проверка → UI. Если показ проводится на моках, схема обозначается как архитектура, а не запись действующего пути. Количество агентов или анимированные значки сами по себе не подтверждают оркестрацию.

## 4. Двухминутная история

Подтверждённый тайминг сохранён: 0–15 боль, 15–25 подход, 25–90 основное демо, 90–105 устройство, 105–120 результат/следующий шаг. Вводная не раскрывает ответ. История NIOSH и Chevron не подменяет Palisades и не добавляется в основной ролик.

| Время полного видео | Показ | Что должен понять зритель |
|---|---|---|
| 0–15 | Оператору нужно следить за смыслом последовательных радиосообщений | Проблема — установить, что было запрошено и подтверждено |
| 15–25 | Обещание связать обмен с источниками; стартовый экран на паузе | Система работает в контексте радио |
| 25–33 | При необходимости краткое Hide/Show Copilot на одинаковых данных | Чем источник отличается от агентского слоя |
| 33–45 | Start; назначение; проверка; ответная реплика; обновление цепочки | Самостоятельное обновление по поступающим данным |
| 45–57 | Оператор открывает подтверждающий аудиоинтервал | У результата есть проверяемое основание |
| 57–73 | Вопрос о переходе всех участников | Агент не подменяет отсутствие доказательства уверенностью |
| 73–85 | Короткий доклад руководителю, ролевая сцена | Конкретное действие человека после проверки |
| 85–90 | На экране остаётся связанный обмен | Завершён один целостный сценарий |
| 90–105 | Фактический запрос/схема текущего подключения | Какая часть технологии реально работает |
| 105–120 | Измеренный результат, если он есть; иначе план пилота | Следующий проверяемый шаг без выдуманной эффективности |

Переключение Hide/Show факультативно: если зритель и так понимает две области, отдать эти секунды прослушиванию. Радио и диктор не должны перекрывать друг друга. Интервалы по ASR предварительно прослушать и убедиться, что они понятны.

## 5. Критерии готовности демонстрации

Первый барьер — понятность: новый зритель за пять секунд объясняет, кто работает с экраном, что проверяет Copilot и где источник. Это целевой тест, ещё не полученный результат. Вторая проверка — после финала зритель не считает доказанным переход всей группы или безопасность людей.

Техническая приёмка: на старте отсутствуют будущие данные; назначение и ответ поступают раздельно; проверка обновляется после публикации. Открывается правильный интервал. При удалении ответной реплики третье звено не становится найденным. Ошибка запроса имеет собственное состояние. После reset не показываются ответы предыдущего поколения. Опоздавшее SSE-событие не возвращает старую revision. Все эти проверки нужны на реальном адаптере повторно; успех локального мока не переносится автоматически на сервер.

Финальный критерий честности: явно разделены созданное на хакатоне, внешние компоненты, реальное архивное аудио, машинный текст, синтетические данные и подключённая модель. Это одновременно полезно для понимания архитектуры и соответствует требованиям происхождения проекта.

## 6. Рекомендация по позиционированию

Предлагаемая фраза для объяснения продукта: **«Copilot связывает радиообмен и показывает, что уже подтверждено, пока оператор следит за инцидентом».** Английский вариант: **“Keep the radio exchange in view. Know what is supported.”** Это предложение для следующей редакции подачи; согласованная вводная не переписывается автоматически.

Не использовать «мы спасаем жизни» как доказанный результат. Допустимо объяснить, что качественная коммуникация важна для безопасности, а наш пилот проверяет конкретное звено этой работы. Сильное впечатление должно возникать из реального источника, автоматического обновления, проверяемого вывода и действия человека.
