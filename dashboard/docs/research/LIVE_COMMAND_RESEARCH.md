# Firewatch: быстрый обзор командных экранов и подключение к main

12 сентября 2026. Изучены реализации main до `8294ebf`: agent-service, его `/agent/v1` DTO, новый reducer радиоканала, импорт платформы, State Machine bridge, прежние макеты Palisades V3/V4. Цель — рабочий интерфейс для уже существующих источников и серверных выводов.

## Визуальные ориентиры

| Первичный источник | Полезный принцип | Применение в Firewatch |
|---|---|---|
| [Tablet Command](https://www.tabletcommand.com/) | Контекст инцидента, командная доска и история действий находятся рядом; карта и исходные материалы доступны в той же системе | Постоянные часы, источники на плане, общая лента и переход к первоисточнику |
| [First Due Command](https://www.firstdue.com/products/command) | Настраиваемые таймеры и LogView с фильтрами и мультимедиа поддерживают наблюдение за изменениями | Единые часы replay, фильтры событий, камеры и радио в основном рабочем экране |
| [Intterra](https://www.intterra.io/solutions) | Общая оперативная картина связывает географический контекст и сведения от источников | Компактная схема помещений с состояниями устройств; не заменяет точный план здания |

Это заимствование принципов компоновки, не заявление о соответствии профессиональным системам или стандартам. Экраны продуктов не копировались. Тёмная палитра выбрана по запросу пользователя: угольный фон, нейтральные панели, янтарный акцент действий, бирюзовый статус свежести. Цвет сопровождается текстом; декоративные шкалы не создают оценку риска из воздуха. Мини-графики строятся по опубликованным измерениям.

Главная последовательность работы: увидеть изменение → открыть источник → прослушать/просмотреть запись → прочитать связанный вывод агента и ограничения → при необходимости задать вопрос. Сырые показания и текст источника не превращаются на фронтенде в тактическую команду.

## Три разных контура

```text
State API ── snapshot + SSE ──→ датчики / лента / общие часы UI
         └── fMP4 HTTP ───────→ камеры / радио UI
         └── bridge ──────────→ Data Platform readings
                                     │ MCP query_telemetry
                                     ↓
                             scoped importer агента
                                     ↓
                     extraction + reducer + question worker
                                     ↓
                           /agent/v1/state и evidence
                                     ↓
                         проверки / ответы / основания UI
```

1. **State API** воспроизводит исходные наблюдения, не распознаёт видео и не интерпретирует радио. Generation, sequence и cursor определяют согласованность доставки. Видео разрежено во времени; пауза/seek/reset общие для подписчиков одного run. Число людей отсутствует, его нельзя получать из считывания пропуска.
2. **Data Platform** хранит reading IDs, телеметрию и опциональные incidents/dashboards, предоставляет REST, Redis SSE и MCP. Bridge сохраняет State evidence ID в `external_event_id`; provenance содержит run/generation и время симуляции. `radio_audio` без текста пропускается; `radio_transcript` становится reading с текстом, но `audio_url` пока null. Камера — `video_event` с метаданными, не результат компьютерного зрения. `ts=received_at` не является абсолютным таймкодом исторического аудио.
3. **Агент** импортирует ограниченный набор чтений и хранит свои проекции в SQLite. Фоновая роль извлекает факты; отдельная роль отвечает на вопрос. Связывание запроса/назначения/ответа радиоканала выполняет reducer. Совпадение канала и временная близость не доказывают личность говорящего или переход всех участников. UI показывает эти ограничения.

В main уже реализован scoped platform polling; интервал фиксирован и ограничен, импорт не двигает часы. Реальная модель, импорт и качество извлечения на записи Palisades не были проверены этой UI-задачей. По ответу пользователя развёрнутых URL агента и платформы пока нет.

## Граница UI и агента

| Данные/действие | Реальный API | Правило интерфейса |
|---|---|---|
| Начальное состояние | GET `/agent/v1/state` | Snapshot membership авторитетно, старые ревизии не откатывают новые |
| Изменение | GET `/agent/v1/events` SSE | Уведомление для перечитывания state; нет обещания replay; периодическая сверка |
| Вопрос | POST `/agent/v1/questions` | Полный context, UUID client_request_id, language; queued/running — не готовый ответ |
| Отмена | POST `/questions/{id}/cancel` | Реальный серверный вызов; не только скрытие карточки |
| Карточка | GET `/cards/{hypothesis_id}` | assessment, lifecycle, publication_status, platform_status независимы |
| Первоисточник | GET `/evidence/{id}` | Проверка контекста, чтение raw_reading, origin/verification, интервалы |
| Аудио агента | Evidence.audio | Только available + playback_url; pending/missing явно подписаны, без подмены другой записью |
| Объяснение | claims + unknowns + coverage + queries | Тип утверждения, ссылки, фактические пределы и запросы сохраняются |

Все GET и cancel передают `demo_context_id`, `generation`, `subject_id`. Сброс State run автоматически не сбрасывает чужой agent context. Согласование этих двух часов — задача интеграции backend; UI не присваивает произвольные platform reading IDs сырым State событиям.

Первый runnable вариант находится в `dashboard/live/`. Нативная медиа-часть проверяется на настоящем State сервере; возможности агента — на его реальном локальном API с явно помеченным FixtureEngine и отдельной синтетической сессией.
