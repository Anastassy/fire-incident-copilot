# Интеграция, роли и приёмка

## Путь данных

State Machine / фиксированный replay → адаптер → Safety Telemetry Platform → REST/SSE интерфейса и read-only MCP агента → производные ответы/карточки → исходное доказательство.

Бинарное медиа может доставляться источником через resolver; состояние и ссылки согласуются с Data Platform. Не строить две конкурирующие версии текущего состояния. Общий ключ платформы держать за серверным прокси приложения.

## Задачи и ответственность

| Участник | Зафиксированная зона | Что передать/сделать |
| --- | --- | --- |
| Настя | Дашборд, взаимодействие с человеком | Один экран, состояния, журнал, evidence viewer, вопрос и карточка |
| Виталий И. | Симуляция и публикация исходных данных | Воспроизводимый эпизод, ID/время/происхождение; для Palisades — аудио и prerecorded text |
| Виталий Н. | Data Platform | Рабочие параметры доступа, проверка payload, REST/MCP-чтение |
| Артём | Получатель этого пакета | Конкретная исполнительская роль не зафиксирована; не приписываем владение агентом или адаптером |
| Нужно назначить | Адаптер, agent→UI, media resolver | Согласовать владельцев перед реализацией |

## Минимальные договорённости

- State Machine: использовать документ 0.2.2, схема 0.2; Bearer, run/generation, SSE cursor, fMP4. Работа сервера описана поставщиком, наше соединение не проверено.
- Data Platform v1: X-API-Key, REST + SSE без replay; источник чтений для UI/агента. После обрыва перечитать REST; для телеметрии восстановить нужный интервал. SSE telemetry не содержит reading.id.
- Адаптер сохраняет source ID, run/generation, времена и provenance. Отдельный namespace внешних device ID на прогон; согласованный список UUID ограничивает выборку. Серверного run_id-фильтра платформы нет.
- Для выбранного Palisades предложено `metric_type=other`, `payload.kind=radio_transcript`; фильтрация payload после чтения. Это предложение адаптера, не реализованное новое API. Сохранять derived происхождение, машинный статус и интервалы.
- Ссылки используют настоящий integer reading_id, device UUID и исходный media/stream ID. Истекающий ticket не постоянный идентификатор. Viewer разрешает reading через кэш/поиск по устройству и времени с проверкой ID; отдельного GET reading/id нет.
- Карточки не создаются через create_incident с обязательной severity. Использовать отдельный производный agent→UI контракт без рейтингов.

## Agent→UI: основа для согласования

Контекст: request_id, demo_context_id, объект (room_id для комнаты; для радио нужен согласованный идентификатор темы/канала), as_of, question. Ответ: контекст, status, claims[], unknowns[], queries[], completed_at. Claim: claim_id, text, evidence[] с reading_id/device_id/временем и опциональным аудиоинтервалом. Карточка: hypothesis_id, контекст, statement, status, claims[], checked_at, revision.

Queries содержит фактический инструмент, фильтры, время, успех/ошибку и полноту выборки; секретов нет. Это проектная схема, не полученный работающий endpoint. Необходимо согласовать метод вопроса и доставку обновлений карточек.

## Критерии готовности общего MVP

- Оба режима агента выполняют реальные запросы; фиксированы входы, но не заготовленный ответ под видом работы агента.
- Каждое подтверждённое утверждение открывает соответствующую запись/интервал.
- Неизвестное остаётся неизвестным; неполный/ошибочный поиск не доказывает отсутствие события.
- После новых данных обновляется та же карточка; после смены прогона нет старых ответов.
- Никаких будущих данных, severity, тактических команд и скрытых агентом событий.
- Контрольный прогон с изменёнными входами меняет результат.
- Пройден ролик на 120 секунд с живым демо 0:25–1:30; см. [тайминг](04_VIDEO_TIMING.md). Это ориентир пользователя, не подтверждённый официальный лимит.

Для текущего Palisades: назначение и подтверждение имеют отдельные основания; подтверждение реплики не доказывает переход всей группы; нужные интервалы вручную прослушаны.

## Приоритеты сильного показа

Одна сцена, одна неопределённость, одно видимое обновление после проверки. Таймер показывает обоснованное время события/проверки. Измерять реальные задержки, корректность и ошибки; не соединять длительность исторической трагедии с временем ответа нашего API в фиктивное «до/после». Исследования обосновывают проблему, не доказанный эффект продукта.

## Открытые решения

Владельцы адаптера/агента/resolver; методы agent→UI; сетевое подключение; ручная проверка радио для выбранного эпизода. Готовность сервера по документам не равна готовности интеграции и браузерного плеера.
