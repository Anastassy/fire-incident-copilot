# Контракт передачи состояния · v0.2

**Версия для первой серверной интеграции, 12 сентября 2026.**
Версия схемы `0.2`, версия документа `0.2.2`, HTTP-префикс `/api/v1`.
Пакет содержит схемы для интеграции и отдельные фикстуры для разработки интерфейса.
Реализация сырого API находится в `state_api/`; результаты развёртывания фиксируются отдельно.
Файлы examples остаются синтетическими, их URL не предназначены для загрузки.
Работающее локальное демо имеет другой, прежний `/api/*` API.

## 1. Граница проекта: данные источников

**State Machine воспроизводит и передаёт данные источников. Распознавание и анализ
выполняет отдельный слой в другом проекте.** Этот договор заменяет первый draft v0.1.

| Данные | Что отдаёт State Machine |
|---|---|
| Датчики дыма и температуры | Исходное значение, единицы, время, качество и свежесть |
| Камеры | Видео/кадры, идентификатор камеры, ссылки загрузки и временной интервал |
| СКУД | События считывателя/двери, направление и зарегистрированные проходы |
| Число людей | Значение только при наличии прямого поля подсчёта в источнике; иначе null |
| Радио | Исходное аудио и готовый текст пакета, временные метки и происхождение |
| Система | Часы, доступность источников, задержка, потери и технические ошибки |

Наш слой выполняет чтение датасетов, нормализацию полей и единиц с provenance,
нарезку/перекодирование медиа для доставки, детерминированный replay и хранение
последних показаний. Технические операции не должны добавлять смысл в наблюдение.

Внешний слой самостоятельно забирает аудио/видео, распознаёт речь и изображения,
определяет говорящих, оценивает опасность и присутствие людей, формирует выводы.
Готовый текст Palisades воспроизводится отдельными radio_transcript-наблюдениями.
В этом API нет Context, Conclusion, результатов CV, режимов ASR,
пороговой классификации пожара или endpoint для приёма результатов анализа.
Внешний слой хранит свои результаты у себя и ссылается на run_id, generation,
evidence_id и media_id исходных данных. Его API не входит в этот договор.

Файлы пакета:

- [openapi.json](openapi.json) — HTTP-пути, тела и JSON Schema объектов.
- Этот README — поведение часов, SSE, медиа, ошибок и восстановления.
- [CLIENT_FLOW.md](CLIENT_FLOW.md) — последовательность интеграции.
- [examples/](examples/) — вымышленные данные; [manifest.json](examples/manifest.json) задаёт схемы.
- [examples/stream.sse](examples/stream.sse) — поток от снимка до паузы.
- [CHANGELOG.md](CHANGELOG.md) — изменения контракта.

Поля, типы и обязательность берутся из OpenAPI; семантика — из README.
Актуальный адрес и результаты проверки смотрите в инструкции подключения из пакета.

## 2. Транспорт и адрес

Адрес сервиса: `http://127.0.0.1:8787/api/v1`.
Базовый URL должен быть настройкой клиента, а не константой в компонентах UI.

```mermaid
sequenceDiagram
    participant UI as Интерфейс
    participant API as State Machine
    participant External as Внешний слой — другой проект
    UI->>API: POST /runs
    API-->>UI: run_id, generation=0, paused
    UI->>API: GET /runs/{run_id}/stream
    API-->>UI: SSE snapshot
    External->>API: GET stream того же run
    API-->>External: SSE snapshot
    UI->>API: POST commands — play
    loop Пока идёт replay
        API-->>UI: Сырые наблюдения и технические состояния
        API-->>External: Те же наблюдения, media_id и время
        External->>API: GET metadata, затем content_url
        API-->>External: Аудио/видео как HTTP bytes
        External->>External: Распознавание и анализ в другом проекте
    end
    UI->>API: POST commands — pause
    API-->>UI: run.updated; часы остановлены
```

HTTP JSON используется для команд, снимка, истории и метаданных. **SSE** используется
для однонаправленной доставки событий сервера. Видео/аудио передаются отдельными
HTTP-ответами; base64 и бинарных данных в JSON/SSE нет. WebSocket, WebRTC, RTSP,
HLS и загрузка новых датасетов пользователем в v0.2 не требуются.

Текстовые JSON/SSE-ответы — UTF-8; медиа передаются в своём бинарном формате.
Числа времени сценария — целые миллисекунды, не секунды.
Идентификаторы — непрозрачные строки с учётом регистра, не отображаемые имена.
`null` означает неизвестное/неприменимое значение, `[]` — известное отсутствие элементов.
Пропущенное поле не эквивалентно `null`: обязательность задаётся схемой.

## 3. Авторизация и браузер

- Все `/api/v1` endpoints, кроме `/health`, требуют **токен приложения**:
  `Authorization: Bearer <application_access_token>`.
- Команда backend выдаёт токен перед сетевой интеграцией; пользовательский login/SSO
  и endpoint выдачи токена находятся вне v0.2. Для разработки доступны фикстуры.
- Права приложения: `state:read` для GET/HEAD/stream и `run:control` для создания
  run и команд. Токен также ограничивает доступные runs/проект. `403` — недостаточно прав.
- Провайдерские Cloudflare/Hetzner/1Password-ключи остаются на стороне инфраструктуры;
  они не являются токенами этого API и не передаются UI.
- Для SSE с Bearer используйте `fetch` и потоковый SSE-парсер. Нативный `EventSource`
  не имеет параметра произвольного заголовка Authorization; токен приложения в URL не передаём.
- CORS разрешает согласованные origin интерфейсов; методы GET/HEAD/POST/OPTIONS;
  request headers Authorization, Content-Type, Idempotency-Key, Last-Event-ID, Range, If-Range.
  Expose-Headers: Content-Length, Content-Range, Accept-Ranges, ETag, Retry-After, X-Request-ID.
  Preflight OPTIONS не требует Bearer и не изменяет состояние. Cookies не нужны.
- Для `<video>`, `<audio>` и `<img>` сервер отдаёт `content_url` с коротким `ticket`.
  Ticket разрешает только GET/HEAD данного media/run/generation, живёт 120 секунд
  по умолчанию. Точный срок — `url_expires_at`; после истечения повторно запросить Media.
  URL не является идентификатором медиа. Использовать `Referrer-Policy: no-referrer`.
- Истёкший Bearer даёт `401`; открытый stream закрывается при истечении доступа.
  Автоматический бесконечный повтор с тем же просроченным токеном запрещён.

## 4. Создание, Play и команды

В v0.2 сценарий выбирается **при создании запуска**. Каждый run изолирован от другого
и имеет собственные часы, журнал и generation. Несколько клиентов одного run видят
одни данные; команда из любого клиента с `run:control` влияет на этот run.
Доступные сценарии и режимы получаются из `/scenarios`, не зашиваются в UI.

```http
POST /api/v1/runs
Authorization: Bearer <application_access_token>
Idempotency-Key: 2a76093f-b143-43ac-89ad-5d13f2436c43
Content-Type: application/json

{"scenario_id":"degraded","speed":1}
```

Ответ `201` — объект Run: `run_id`, `generation=0`, `status=paused`, `sim_time_ms=0`,
`duration_ms`, `scenario_version`, `links`. Наблюдения, допустимые на t=0, уже могут
присутствовать в начальном снимке. Пример `contract-demo` из фикстур не обязан быть
в каталоге сервера. Параметра analysis_mode нет: распознавание не управляется этим API.

Открыть stream, принять snapshot, затем отправить:

```http
POST /api/v1/runs/{run_id}/commands
Authorization: Bearer <application_access_token>
Content-Type: application/json

{"command_id":"569f86c0-3555-4f0a-9b9f-539258dcb570","expected_generation":0,"action":"play"}
```

`200 CommandResult` означает, что команда применена и её событие записано в журнал.
`applied_sequence` указывает событие команды. Это подтверждение не гарантирует, что
UI уже прочитал соответствующий SSE-кадр. Не перезаписывайте свежий UI старым HTTP-ответом.

| action | Дополнительные поля | Результат |
|---|---|---|
| `play` | — | `paused → playing`; уже playing — успешная пустая операция |
| `pause` | — | `playing → paused`; часы и выдача будущих наблюдений останавливаются |
| `set_speed` | `speed: 1 \| 10 \| 60` | Смена множителя часов, без сброса |
| `reset` | — | generation + 1, время 0, status paused, скорость 1 |
| `seek` | `position_ms` от 0 до duration | generation + 1, пересчёт до момента, status paused, скорость сохраняется |

`completed` означает конец сценария. Play из completed возвращает `409 RUN_COMPLETED`;
для повтора нужен reset. В error разрешены reset/seek, остальные команды дают
`409 RUN_ERROR`. Seek на duration оставляет paused; Play даст RUN_COMPLETED.
Новый сценарий — новый POST /runs, а не изменение scenario_id существующего run.

Сервер выполняет команды последовательно. `expected_generation` обязателен:
несовпадение — `409 GENERATION_MISMATCH` с текущим generation. Для конкурирующих
Play/Pause в одном поколении действует порядок приёма сервером.

Дедупликация обязательна:

- POST /runs: одинаковый Idempotency-Key и тело в рамках одного субъекта авторизации
  возвращают тот же run и 201. Ключ хранится минимум до expires_at run.
- Команды: одинаковый command_id и тело в рамках run возвращают оригинальный результат,
  без повторного reset/seek и без нового события. Проверка дубликата **предшествует**
  проверке generation. ID с другим телом — `409 IDEMPOTENCY_CONFLICT`.
- После сетевого timeout клиент повторяет тот же ID и тело. Новый ID означает новую команду.

## 5. Общие часы, generation и воспроизводимость

- `sim_time_ms` — положение в сценарии. `speed=10` означает 10 секунд сценария за
  секунду реального времени. Сервер использует монотонные часы для продвижения.
- `observed_sim_time_ms` — когда наблюдение относится к сценарию;
  `received_sim_time_ms` — когда оно стало доступно движку. Второе не меньше первого.
- `emitted_at`, `received_at`, `server_time` — реальные UTC RFC 3339.
- `provenance.recorded_time` сохраняет исходное время независимого датасета.
  Например, NIST — секунды опыта, Broadcastify — Unix-время начала файла + аудиосмещение.
  Точный пересчёт описан в `provenance.time_mapping`.
- Каждое изменение получает монотонный `sequence` внутри run, начиная с 1. Он не
  сбрасывается при reset/seek. Порядок доставки определяется sequence, а не timestamp.
- Generation начинается с 0, увеличивается при reset/seek. Запросы
  истории, медиа и кеши потребителей привязаны к run + generation. Старый ответ не применяется
  к новому поколению. scenario_version неизменна внутри run.
- На ускорении обрабатываются **все** наблюдения. UI может объединять перерисовки,
  но журнал не теряет исходные наблюдения и переходы доступности.
- Версия сценария фиксирует источники, преобразования и моменты публикации.
  Повторный replay воспроизводит те же значения и порядок исходных наблюдений;
  реальные timestamps и идентификаторы нового run могут отличаться.
  Скорость/очередь обработки внешнего проекта не тормозит наши часы автоматически.

## 6. SSE: начальный снимок, события, переподключение

`GET /runs/{run_id}/stream` возвращает `Content-Type: text/event-stream`.
Ответ потоковый: `Cache-Control: no-cache, no-transform`, отключён buffering reverse proxy,
кадры flush сразу, долгий read timeout. Серверный интервал обработки целевой 100 мс;
тик сервера — 250 мс, SSE-события отправляются после обработки. Сетевая задержка
зависит от соединения; значение 250 мс не является гарантией end-to-end latency.

**Без курсора** первый именованный кадр — `snapshot` с полным Snapshot и
`id: <snapshot.as_of.cursor>`. Сервер атомарно фиксирует снимок и границу журнала,
затем выдаёт события строго после `as_of.sequence`; между снимком и подпиской нет дыры.

**С курсором** передайте `Last-Event-ID: <cursor>` либо `?after=<cursor>` — только один
вариант. Сервер выдаёт события после курсора, затем новые. Снимок повторно не выдаётся.
Курсор непрозрачен; клиент хранит его целиком. В примерах `run-demo-001:1` — только формат фикстуры.

```text
id: run-demo-001:1
event: event
data: {"schema_version":"0.2","event_id":"evt-demo-1","run_id":"run-demo-001","generation":0,"sequence":1,"cursor":"run-demo-001:1","kind":"run.updated","sim_time_ms":0,"emitted_at":"2026-09-12T10:30:00Z","data":{"run_id":"run-demo-001","...":"см. полный examples/stream.sse"}}

```

Сокращение `...` выше объяснительное; **полный валидный пример** — в `examples/stream.sse`.
Поле SSE `id` равно `Event.cursor`. Поле SSE `event` для всех журналируемых изменений
равно `event`, а конкретный тип находится в JSON `kind`.

| Имя SSE-кадра | JSON | Сохраняется в журнале / меняет cursor |
|---|---|---|
| `snapshot` | Snapshot | Начальная граница; сохранить его cursor после применения |
| `event` | Event | Да; sequence уникален в run |
| `heartbeat` | Heartbeat | Нет; **без id**, cursor не продвигает |
| `stream_error` | Error | Нет; соединение закрывается |

Heartbeat каждые 5 секунд реального времени, в том числе на паузе и после completed.
После 15 секунд без байтов/heartbeat UI показывает потерю соединения; последнее
состояние остаётся видимым с отметкой давности. Не превращать обрыв SSE в состояние
«все датчики disconnected»: связь UI↔сервер и связь прибор↔движок — разные вещи.

Доставка — **at least once**. После успешного применения сохраняются sequence и cursor.
Повтор уже применённого sequence игнорируется. После паузы клиента его cursor может
отстать, но heartbeat.last_sequence не позволяет пропустить непрочитанные события.
В v0.2 нет фильтрации SSE-потока: все события run приходят по единой последовательности.
Неизвестный kind в совместимой minor-версии можно игнорировать, продвинув cursor;
иначе при неизвестной major-схеме остановиться с сообщением несовместимости.

Журнал сохраняется на весь срок run; expires_at — минимум 24 часа после создания.
Точные сроки сообщает Run. Недействительный cursor — 400; cursor другого run — 409;
утраченный/просроченный cursor — `410 CURSOR_EXPIRED`. Истёкший run — `410 RUN_EXPIRED`.
При CURSOR_EXPIRED получить снимок и подключиться после его cursor, либо открыть stream
без cursor. При RUN_EXPIRED создать новый run по явному действию пользователя.

Переподключение: паузы 1, 2, 4, 8, 15 секунд с небольшим jitter; `Retry-After` имеет
приоритет. `401/403` не повторять бесконечно. Медленный клиент получает
`stream_error: BACKPRESSURE_RESYNC` и отключается; уже журналируемые события не теряются.
Run и журнал сохраняются при рестарте процесса. После восстановления часы paused;
возобновление требует Play, а не тайного продвижения за время остановки сервера.

При reset/seek сервер сначала записывает `stream.reset` с **новой generation**.
Это барьер: клиент останавливает плееры, отменяет старые fetch, очищает состояние
прошлого поколения, получает Snapshot и продолжает после его cursor. Сервер не
пересылает весь внутренний пересчёт seek как пачку «новых реальных» наблюдений.
Пересчитанная история доступна через GET; новый снимок содержит итог на выбранное время.
Ответ от старой generation отбрасывается даже если HTTP завершился позже нового.

## 7. Типы событий и применение данных

Payload — **полный объект**, не JSON Patch. `device.updated` заменяет объект
устройства с данным device_id. Наблюдения неизменяемы и добавляются по evidence_id.

| kind | data | Действие потребителя |
|---|---|---|
| `run.updated` | Run | Обновить часы и управление |
| `observation.created` | Observation | Добавить исходное наблюдение |
| `device.updated` | DeviceState | Заменить последние показания и доступность прибора |
| `room.updated` | RoomState | Обновить перечень недоступных приборов комнаты |
| `camera.updated` | CameraState | Обновить ссылку на последний clip/frame |
| `access.updated` | AccessSummary | Обновить счётчики зарегистрированных проходов |
| `occupancy.updated` | Occupancy | Обновить последнее число из источника или null |
| `radio.channel.updated` | RadioChannel | Обновить канал и последнее аудио |
| `system.updated` | SystemHealth | Обновить техническую диагностику |
| `stream.reset` | StreamReset | Барьер поколения; загрузить новый снимок |

Observation.kind: measurement, camera, access, radio_audio, people_count, connectivity.
Поле data зависит от kind в OpenAPI. evidence_id — неизменяемый ID исходного
наблюдения; слово evidence не означает, что сервис сделал аналитический вывод.
Наблюдение публикуется до состояния, которое на него ссылается. Старые наблюдения,
на которые ссылается начальный снимок, доступны через GET evidence.

Snapshot включает run, devices, rooms, cameras, access, occupancy, radio.channels
и system. Новому потребителю, которому нужна полная история аудио или показаний,
нужно прочитать observations; snapshot содержит только последнее состояние.

Run/system обновляются максимум раз в 250 мс при изменении; availability-переходы
и исходные наблюдения не объединяются. Для отображения часов используются run,
event.sim_time_ms и heartbeat; интерполяция UI не создаёт новые показания.

## 8. Датчики и техническая свежесть

Reading передаёт metric, value, unit, availability, observation_id,
observed_sim_time_ms, age_ms и stale_after_ms. Метрики открыты для расширения:
temperature, obscuration, smoke_detected, co, eco2 и другие каналы источников.
Сервис не присваивает значениям метки normal/warning/alarm по своим порогам.
Дискретный аппаратный сигнал допускается как boolean-показание с происхождением;
разметка датасета Fire Alarm не является аппаратным наблюдением.

| Поле | Значения и смысл |
|---|---|
| availability | fresh / stale / missing / invalid / disconnected |
| measurement.data.quality | valid / missing / invalid — качество исходного значения |
| value | число, boolean или null; ноль — реальный ноль |

Missing/invalid Observation имеет value=null. Последнее значение сохраняется при
stale/disconnected с исходным observation_id и возрастом. На паузе age_ms по шкале
сценария не растёт. При age_ms >= stale_after_ms показание stale. У каждого канала
своя availability; DeviceState показывает общую доступность устройства.
Уведомление connected ещё не делает показания fresh: нужны новые данные.

RoomState содержит справочные IDs и перечень недоступных устройств. SystemHealth
показывает здоровье доставки/часов/моста Blender; healthy не означает безопасность
здания. Оценка пожара, маршрутов и содержимого комнаты относится к внешнему слою.

Единицы сохраняются: NIST obscuration может быть %/ft, температура — degC.
eco2 означает эквивалент CO₂, не CO. Преобразования единиц описаны в provenance.
Пропуски не заполняются нулями. Координаты — метры, Z-up, либо null.

## 9. СКУД и исходное число людей

СКУД-события различают предъявление пропуска, разрешение/отказ и обнаруженный проход.
access_granted не означает passage_detected. subject_ref — псевдоним, не ФИО.
passage_count заполняется только для соответствующего сигнала прохода, иначе null.
AccessSummary суммирует только зарегистрированные passage_detected с известным
направлением и passage_count в полуоткрытом окне [window_start, window_end).
При полном покрытии такого источника отсутствие проходов даёт 0; если источник
не регистрирует проходы или покрытие неполное — null. Пропуск не считается человеком.

Occupancy хранит последнее прямое наблюдение people_count для scope:

- basis=source_count: observation_id указывает исходную запись с count/unit/quality.
  Число и качество копируются, сервис не подтверждает физическое присутствие.
- basis=unknown: count=null, observation_id=null; подходящего источника пока нет.
- Отрицательное число запрещено; настоящий ноль остаётся нулём. Missing/invalid
  исходное значение — null; старое значение может сохраняться со stale/disconnected.

В базовом демо потока прямого подсчёта людей нет. Оценка по камерам, пропускам,
радиодокладам или объединению источников выполняется другим проектом. Поле count
не заполняется скрытым числом участников синтетического сценария.
Общая цифра берётся из scope_type=building, если такой источник есть; значения
комнат и здания автоматически не складываются.
Отдельные примеры observation.people-count.json и occupancy.source-count.json
показывают условный источник числа 12. Они не входят в основной stream.sse,
где после события пропуска число людей остаётся неизвестным.

## 10. Непрерывное видео/аудио и доступ к отдельным фрагментам

**Основной режим просмотра/анализа — непрерывный HTTP-поток.** Клиент один раз
читает GET `/runs/{run_id}/media-streams`, затем один раз открывает content_url
для каждого нужного устройства. По этому соединению сервер сам передаёт bytes.
Регулярного GET состояния или запроса каждого медиасегмента не требуется.
Пример метаданных — [examples/media-streams.json](examples/media-streams.json).

- Путь: GET `/runs/{run_id}/media-streams/{stream_id}/content?generation=G`.
  Авторизация: Bearer либо краткоживущий ticket из MediaStream.content_url.
- Формат: fragmented MP4, видео H.264 (`video/mp4`), аудио AAC (`audio/mp4`).
  Сначала ftyp/moov с настройками декодера, затем moof/mdat по часам run.
- До Play выдаются только настройки декодера. Фрагмент с samples отправляется,
  когда целиком достигнут его временной интервал. Целевой размер — около 2 секунд.
- Pause удерживает соединение и прекращает выдачу новых samples. Уже полученные
  bytes могут оставаться в буфере плеера; UI ставит свой плеер на паузу по run.updated.
- При подключении позже начала записи сначала передаются уже доступные фрагменты
  от начала этой записи, затем соединение ждёт новые. Это не обещание нулевой задержки.
- Reset/seek закрывает старый поток. Клиент получает новую generation из SSE,
  заново запрашивает MediaStream и открывает новый content_url. Конец тестовой записи,
  истечение run, потеря канала или отключение клиента также завершают соединение.
- Ticket проверяется при открытии соединения. По истёкшему URL нужно получить новый.
  Byte Range и Content-Length в непрерывном ответе не используются; Accept-Ranges: none.
- Доступно до 24 потоковых соединений суммарно, включая SSE. Превышение — 429.
- Другой слой может читать ответ потоковым HTTP-клиентом/демультиплексором fMP4.
  В браузере используется совместимый MP4-плеер, при необходимости MediaSource;
  порядок получения bytes не означает автоматическую синхронизацию UI-плееров на 60×.

В первой выборке только два тестовых видео (FP19 и FP2, до 30 секунд) и два
тестовых аудиоисточника Broadcastify (первые 60 секунд каждого, включая тишину).
Это разные записи, условно сопоставленные сценарию. Автоматического зацикливания нет.
AAC добавляет небольшую задержку кодера; точная поправка указана в provenance.time_mapping.
Счётчик людей и результаты распознавания из этих записей сервис не вычисляет.

**Отдельные Media-фрагменты** сохраняются для истории, повторного просмотра и
обработки выбранного evidence. Это дополнительный доступ, не механизм опроса состояния.

При поступлении `camera` или `radio_audio` Observation клиент получает media_id.

1. GET `/runs/{run_id}/media/{media_id}?generation=G` с Bearer → Media.
2. Если status=ready, загрузить content_url напрямую в video/audio/img или через fetch.
3. Бинарный endpoint поддерживает GET с одним HTTP byte Range: 200/206,
   Content-Length, Content-Range, Accept-Ranges: bytes, ETag. Неверный или
   множественный Range → 416 с `Content-Range: bytes */<length>`.
   HEAD возвращает заголовки полного ресурса без тела; Range в HEAD игнорируется.
4. Если ссылка истекла → повторить GET Media и заменить URL, сохранив позицию.
   media_id и SHA-256 стабильны; ticket и URL могут меняться. Никаких постоянных raw-путей.

Минимальные форматы передачи: видео MP4/H.264, кадры JPEG/PNG, аудио MP3 либо WAV PCM.
Opus/Ogg допускается, если mime_type/codec поддержаны клиентом. Неподдерживаемый
формат исходного датасета backend преобразует в отдельный производный файл с provenance;
исходник остаётся неизменным. Пакет примеров содержит фиктивные URL/хеши, не реальные медиа.

**Полное будущее видео заранее не отдаётся.** В v0.2 replay публикует законченные
самостоятельно декодируемые clips (целевой размер 2 секунды) и отдельные кадры.
`capture_end_sim_time_ms <= published_sim_time_ms <= current sim_time_ms`.
До публикации GET metadata/content возвращает 404. Известный ID не обходит этот барьер.
Для изображения start=end и duration_ms=null. Для видео/аудио duration=end−start;
byte offsets не являются временными offsets.

Таким образом, UI показывает наблюдение с небольшой задержкой до длины фрагмента.
Для непрерывного видео буферизует последовательные доступные clips по chunk_index;
для простой первой версии может показывать последний clip/кадр. Пропущенный chunk
отображается как разрыв, не склеивается незаметно. Исходный длинный файл на несколько
часов не публикуется вместо ограниченного фрагмента.

На 1× режим «Следовать replay» выбирает только уже доступные clips; позиция внутри
clip считается относительно capture_start, с учётом playback_delay_ms камеры.
На 10×/60× видео может показывать ближайший доступный кадр/clip; звук по умолчанию
выключен. Все аудиофрагменты доступны внешнему потребителю независимо от звука браузера.
При Pause автоматическое проигрывание останавливается. Пользователь может отдельно
прослушать уже полученное доказательство в режиме «Просмотр записи», не двигая часы run.
Autoplay со звуком требует действия пользователя в браузере.

Камера передаёт медиа и технические метаданные. Определение дыма, пламени,
людей и прочего содержимого изображения выполняет внешний слой.

## 11. Радио: аудио и готовая расшифровка пакета

Версия 0.2.2 добавляет [синхронное воспроизведение Palisades](PALISADES.md):
radio_transcript приходит через observation.created после соответствующего аудио.
Текст готов заранее, помечен delivery=prerecorded; ASR на сервере не выполняется.
Snapshot хранит latest_transcript, история доступна через observations.

Радионаблюдение содержит channel_id, media_id, chunk_index,
audio_start_sim_time_ms и audio_end_sim_time_ms. RadioChannel хранит доступность
канала и latest_audio_media_id. Media описывает формат, длительность, параметры
аудио, URL загрузки, временное соответствие и provenance.

State Machine не распознаёт слова, язык, говорящих, позывные или смысл разговора;
не классифицирует шум/речь и не выдаёт текстовую замену аудио. Исходная тишина и
помехи сохраняются. Нарезка и необходимое перекодирование описаны в provenance;
семантической фильтрации, удаления пауз и скрытого улучшения записи нет.
Канал приёмника не идентифицирует человека. Отсутствующий chunk означает разрыв
доставки, не тишину. Фрагменты упорядочены по chunk_index и временным интервалам.

Внешний слой подключается к тому же run, получает radio_audio, загружает Media и
обрабатывает аудио у себя. Полную уже опубликованную историю он получает через
GET observations с фильтром device_id радиоканала. Для результатов у него есть
run_id/generation/evidence_id/media_id и точный аудио-интервал; callbacks в этот API нет.

Pause останавливает публикацию будущих наблюдений. Уже опубликованные фрагменты
остаются доступны; heartbeat и технические ошибки соединения продолжают поступать.
Внешний проект может закончить свои задачи на ранее полученных данных независимо
от нашей паузы. После reset/seek он отделяет задачи и результаты старой generation.
Его алгоритмы, очереди и ошибки не входят в SystemHealth нашей state machine.

## 12. Происхождение и история

Наблюдение сохраняет source_id, acquisition_id, device_id, room_id, recorded time,
observed/received sim time, received_at, units и provenance. Origin различает
recorded, synthetic, derived и human_report как происхождение источника; последнее
не означает, что аудио было превращено в текстовый доклад.

Источники независимых опытов сопоставлены только как составной сценарий.
independence_group позволяет внешнему анализатору отличать коррелированные каналы.
Ground-truth labels, YOLO-разметка, скрытая истина сценария и будущие наблюдения
не передаются. Радиозапись из Los Angeles сохраняет source/time/attribution;
условная привязка к офису явно описана в composition_note.

GET /evidence/{id}?generation=G возвращает неизменяемый Observation.
404 означает неизвестное/ещё не опубликованное наблюдение без раскрытия будущего.

GET observations требует generation. Первая страница фиксирует as_of_sequence
и состав выборки; следующие используют next_cursor с теми же фильтрами.
Сортировка — received_sim_time_ms, observed_sim_time_ms, evidence_id.
Интервал [from_ms, to_ms) применяется к observed_sim_time_ms; default from=0,
to=current sim_time_ms+1, limit=100, max limit=500. Будущее не включается.
Старый pagination cursor после смены generation даёт 409; истёкший — 410.
История не заменяет более свежее текущее состояние клиента.

## 13. Ошибки и проверка интеграции

Каждая ошибка содержит error.code, message, request_id, retryable, details.
HTTP-статус и machine code определяют поведение, текст message предназначен человеку.
Ответ HEAD при любом статусе не содержит тела: клиент использует статус и заголовки;
для получения подробностей может повторить запрос методом GET.

| HTTP | Типичные code | Действие клиента |
|---|---|---|
| 400 | INVALID_REQUEST, INVALID_CURSOR | Исправить запрос |
| 401 | UNAUTHORIZED, TOKEN_EXPIRED | Обновить доступ |
| 403 | FORBIDDEN, MEDIA_TICKET_EXPIRED | Проверить право; ticket обновить через Media |
| 404 | NOT_FOUND | Неизвестный или ещё не опубликованный ресурс |
| 409 | GENERATION_MISMATCH, IDEMPOTENCY_CONFLICT, RUN_COMPLETED, RUN_ERROR | Получить актуальный run/snapshot |
| 410 | CURSOR_EXPIRED, RUN_EXPIRED | Восстановить снимок или создать новый run |
| 416 | RANGE_NOT_SATISFIABLE | Исправить byte range |
| 422 | FEATURE_UNAVAILABLE, INVALID_COMMAND | Проверить capabilities, поля и границы времени |
| 429 | RATE_LIMITED | Выждать Retry-After |
| 503 | SERVICE_UNAVAILABLE | Повторить с backoff, показать потерю связи |

Признаки готовой интеграции перед показом:

1. Создание run возвращает paused; первое SSE-сообщение даёт полный снимок.
2. Play продвигает общие часы и передаёт события; 1×/10×/60× не меняют набор исходных наблюдений.
3. Pause фиксирует часы и выдачу будущих наблюдений; опубликованное медиа доступно.
4. Повтор command_id не выполняет reset второй раз; старый expected_generation даёт 409.
5. Переподключение после cursor восстанавливает события без пропусков; дубликаты не удваивают счётчики.
6. Reset/seek меняет generation; старые fetch, clips и результаты внешнего слоя не попадают в новый экран.
7. Клиент получает видео/аудио через HTTP 200/206; URL обновляется после истечения ticket.
8. Будущие evidence/media недоступны даже при известном ID.
9. Missing отличается от zero; disconnected не показывает старое значение как свежее; badge не превращается в подтверждённого человека.
10. Поток содержит исходное аудио/видео, значения и готовый текст из пакета; аналитических выводов в нём нет.

## 14. Реализация в репозитории

Сервис в `state-machine/state_api/` реализует этот контракт. Генератор локального
bundle создаёт синтетические датчики, камеры и радио. Опциональный импорт добавляет
Palisades focus из уже включённого радиоэпизода; реальные корпуса NIST, Smoke Detection
и D-Fire в эту поставку не входят. Список сценариев определяется bundle сервера.

Сервис независим от `agent-service/` и `agent-ui-contract-v0.1/`. Аналитический
слой должен подключить собственный адаптер к SSE/HTTP State API. Наличие обоих
компонентов в одном репозитории не означает готовую сквозную интеграцию.
[Запуск и состав поставки](../../README.md).

## 15. Версии и источники формата

Добавление необязательного поля совместимо: клиент игнорирует незнакомые поля.
Для нового kind в SSE клиент продвигает cursor и сохраняет диагностическую запись.
Изменение смысла/единиц/обязательных полей требует новой major-версии схемы или явного
согласованного перехода, пока документ draft. Не переписываем значения enum молча.
Сервер возвращает фактически поддерживаемые функции через capabilities.

Форматы выбраны по первичным спецификациям: [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html),
[SSE / HTML Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html),
[HTTP Range / RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-14).
Правила run/generation, доставки медиа и состава состояния выше — проектные решения этого договора.
